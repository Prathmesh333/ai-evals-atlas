Chapter 19 / Advanced systems

Safety, robustness, and coverage

Measure failures under changed conditions and test safeguards separately.

Learning level 75–803 min read + practice1 diagram · 1 exercise

Test shifts in the workload

Robustness is performance under relevant changes in conditions. Test misspellings, formatting changes, missing context, different languages, and shifts in domain. Choose changes that match plausible use rather than arbitrary noise.

Report performance by slice. A strong average can hide failures for a small language group or a rare document format. Include sample sizes and uncertainty for each slice. Very small slices cannot support precise comparisons.

For multimodal systems, control image resolution, cropping, audio quality, transcription, and video sampling. A result can reflect preprocessing as much as model capability. Keep those settings in the experiment record.

Evaluate safeguards as systems

A refusal rate alone is not a complete safety measure. Measure appropriate refusal on disallowed requests and unnecessary refusal on allowed requests. The policy and labels must specify the distinction.

Prompt injection places instructions inside untrusted content such as a retrieved page or tool result. Test whether the system preserves the intended instruction boundary. Use controlled fixtures and inspect unauthorized actions as well as the final answer.

Separate capability evaluation from safeguard evaluation. A model can possess a capability while a deployed system restricts access to it. Evaluate the restrictions under the actual tools, permissions, and monitoring configuration.

Red teaming and residual uncertainty

Red teaming searches for failures through targeted exploration. It is useful for discovering failure modes but does not automatically estimate their production frequency. Convert discovered failures into regression cases and add related variants.

Define an authorized scope and isolated environments for risky tool tests. Use synthetic secrets and simulated actions. Preserve evidence of both successful controls and failed controls.

No finite test set proves the absence of harmful behavior. A release decision should connect measured behavior, coverage gaps, impact, and mitigations. State the limits of the evidence rather than labeling an untested system safe.

Try it yourself

Create paired cases for one safeguard: a request that should be refused and a similar allowed request that should be answered.

Does a red-team failure rate estimate how often ordinary users encounter that failure?

Not by itself. Red-team tasks are selected to find failures. Estimate ordinary-use frequency with a representative sample and a declared protocol.
