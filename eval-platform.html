Chapter 16 / Operate and improve

Build an evaluation platform

Turn scripts into a versioned, auditable service with release gates.

Learning level 90–953 min read + practice2 diagrams · 1 exercise

Separate the components

An evaluation platform needs a dataset registry, a run specification, a task runner, model adapters, graders, and result storage. Keep these components separate so you can change a model without silently changing the metric.

The runner schedules cases, enforces budgets, and records failures. A model adapter translates the run specification into a provider request. A grader reads outputs and evidence. An aggregator produces metrics with uncertainty and slice breakdowns.

Use immutable run identifiers. Store case-level outputs before aggregation. If the aggregation code changes, you should be able to recompute metrics without requesting the model again.

Handle operational failures

Retries can change both cost and the meaning of success. Define which failures qualify for retry and how retries count against the budget. Store every attempt rather than keeping only the successful response.

Cache keys should include model revision, prompt, task input, sampling settings, and relevant environment state. An incomplete key can reuse a result from a different experiment. Disable caching when measuring real latency or stochastic variation unless the protocol explicitly includes it.

Sandbox generated code. Apply time, memory, network, and filesystem limits appropriate to the task. A Python subprocess alone is not a security boundary. The included evaluation lab checks stored strings and does not execute generated programs.

Make release gates explicit

A release gate connects metrics to a decision. Example project criteria might require no new critical regression, a minimum task-success rate, and an acceptable latency tail. These thresholds are project choices, not universal standards.

Run a fast smoke suite on each change. Run larger suites when a candidate is ready. Give every failure an owner and a reasoned disposition. A flaky case should be investigated rather than silently disabled.

Export a report with the candidate and baseline configurations, case counts, uncertainty, regressions, cost, and unresolved issues. Keep the evidence even when the candidate is rejected. Failed experiments explain later decisions.

Try it yourself

Draw the data flow from dataset registry to release report. Identify which artifacts must be immutable and which results can be recomputed.

Why store per-case outputs if you already have the average score?

Per-case outputs support audits, error analysis, paired comparisons, and reaggregation after a scoring correction. An average cannot recover that information.
