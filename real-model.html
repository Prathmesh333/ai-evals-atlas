Chapter 27 / Operate and improve

Collect outputs from a real model

Connect the evaluation dataset to a local or compatible hosted endpoint without sending labels.

Learning level 90–983 min read + practice1 diagram · 1 exercise

Separate generation from grading

The existing comparison lab starts with stored predictions. The endpoint collection lab obtains new predictions from a model server. Separating these stages lets you audit generation and revise a grader without paying to generate every answer again.

Each request sends only the case input and a fixed system instruction. Expected answers and slice labels stay in the evaluator. Including the answer key in a model prompt would invalidate the experiment.

The collector uses the common chat-completions request shape. It is not a universal provider adapter. Some servers require different token-limit fields, response formats, or authentication. Inspect the server documentation before interpreting a request error as model behavior.

Run the collector deliberately

Start a model server that supports the required endpoint. Identify its exact model name. Use the lab command with that name and the server's base URL. The default endpoint is local, so no hosted provider receives data unless you select one.

For a hosted endpoint, provide an API key through the AI_EVAL_API_KEY environment variable if required. Do not place a key in a command that you publish or in the repository. Requests can incur charges under the selected provider's terms.

Use data that you are permitted to send to the chosen endpoint. The included dataset is synthetic. The collector does not upload training files, hidden labels, or arbitrary workspace files.

Record failures and timing honestly

The script sends one sequential attempt per case, with a timeout and a fixed output budget. It stores successful answer strings in predictions.json and records attempt metadata in manifest.json. Failed requests remain absent from predictions and count as failures in the comparison lab.

The timer measures non-streaming request duration. It does not measure time to first token, concurrent throughput, or server-only compute time. Usage fields are recorded only when the endpoint returns them.

The manifest identifies the requested model, endpoint, settings, case hash, and request status. A requested model alias may change at the server. For a strict reproduction, also record the server's resolved checkpoint and serving configuration.

Compare real runs fairly

Collect baseline and candidate outputs on the same cases with declared settings. Pass both prediction files to evaluate.py. Do not compare a real model against the sample synthetic baseline as though both were measured models.

The sample exact-answer grader intentionally penalizes extra prose. If that contract is wrong for your application, revise the contract and grader before comparing systems. Store original outputs so the change is auditable.

The collector's automated tests use a local fake HTTP server to verify request construction and error handling. They are software tests, not model quality measurements. No hosted model result is implied by those tests.

Commands for this note

python labs/collect_predictions.py --model YOUR_LOCAL_MODEL --base-url http://127.0.0.1:1234/v1 --output labs/runs/baseline
# Repeat with the candidate model and a separate output directory.
python labs/collect_predictions.py --model YOUR_CANDIDATE --base-url http://127.0.0.1:1234/v1 --output labs/runs/candidate
python labs/evaluate.py --baseline labs/runs/baseline/predictions.json --candidate labs/runs/candidate/predictions.json
Try it yourself

Collect one baseline and one candidate run. Inspect the manifest, verify that labels were excluded from requests, and explain every failed request.

Should a failed request disappear from the accuracy denominator?

No. Under this lab's protocol it remains a failed task. The manifest records the operational failure so it can be distinguished from an incorrect answer.
