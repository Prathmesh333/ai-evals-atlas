Chapter 17 / Advanced systems

Long context, retrieval, and memory

Test evidence use across position, length, distractors, sessions, and memory updates.

Learning level 70–803 min read + practice1 diagram · 1 exercise

Capacity is not effective use

A context limit states how much input a system accepts. Effective context measures whether the system uses relevant information reliably within that input. The two can differ.

Construct a matrix of input lengths and evidence positions. Place the same fact near the start, middle, and end. Add plausible distractors and contradictory versions. Keep the question and success rule fixed while changing the condition.

A needle-retrieval task tests finding a fact. It does not establish multi-document synthesis, conflict resolution, or reasoning across distant passages. Use several task families rather than reporting a single retrieval percentage as long-context understanding.

Evaluate the retrieval boundary

For an answerable question, identify the evidence needed to support the answer. Measure whether the retriever returns that evidence and whether the generator uses it correctly. For an unanswerable question, define the expected abstention behavior.

An oracle-context experiment supplies the correct evidence directly. If the system still fails, retrieval is not the only problem. Comparing no-context, retrieved-context, and oracle-context conditions helps locate the bottleneck.

Evaluate chunking, reranking, and context assembly with the same question set. A higher retrieval recall can hurt generation if added passages consume the budget or introduce contradictions. More retrieved text is not automatically more useful evidence.

Memory creates a time dimension

Persistent memory stores information across interactions. Test whether the system writes the correct fact, retrieves it later, updates it when it changes, and deletes it when required. Treat each operation as a measurable state change.

Use synthetic users with different facts and isolated memory stores. Check that one user's information does not influence another user's response. Include stale preferences, conflicting updates, and explicit requests not to retain a fact.

Distinguish conversational context, stored memory, and learned model weights. Deleting a memory record does not remove information from model weights. A successful deletion test must identify which storage layer it evaluates.

Design a diagnostic report

Report results by context length, evidence position, task type, and answerability. Include truncation rates and the actual input-token count after template construction. A system can silently truncate the only relevant passage.

For multi-step memory tests, save the state before and after each action. Reset state between independent trials. If the test reuses one evolving memory store, the later cases are not independent measurements.

LongBench provides public long-context tasks and versions. Name the exact version and task selection. Use it alongside application-specific evidence tests rather than assuming its average matches your document workload.

Try it yourself

Create nine cases by crossing three evidence positions with three input lengths. Add one conflicting-document case and one missing-evidence case.

What does failure with oracle context tell you?

The system fails even when correct evidence is supplied. Investigate interpretation, generation, instructions, and grading rather than attributing the entire failure to retrieval.
