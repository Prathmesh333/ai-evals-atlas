Chapter 24 / Advanced systems

Benchmark latency, throughput, and cost

Measure a serving system under realistic load and preserve the quality constraint.

Learning level 85–953 min read + practice1 diagram · 1 exercise

Define the clocks

End-to-end latency measures the time from client request initiation to complete response receipt under a specified boundary. Time to first token measures delay before the first output token. Inter-token latency describes the spacing of subsequent output tokens.

A non-streaming request gives end-to-end timing but does not reveal first-token timing. Do not label its response duration as time to first token. Record whether network time, queueing, preprocessing, and postprocessing are included.

Report latency distributions rather than only the mean. A p95 is the 95th percentile under a stated measurement and aggregation method. Combining percentiles from separate runs by averaging them does not produce the percentile of the combined requests.

Control the workload and load generator

Specify input and output length distributions, concurrency, arrival process, caching, hardware, model version, quantization, and batching. Compare like workloads. Short responses and warm caches can make a system appear faster without improving the target use case.

A closed-loop client waits for a response before sending the next request. When the system slows, offered load decreases. An open-loop generator schedules arrivals independently and can expose queue buildup. Choose the mode that matches the question and report dropped or delayed requests.

Warm up when measuring steady-state performance, but measure cold starts separately if users encounter them. Keep failed requests in the operational report. A throughput figure that ignores rejected requests can hide overload.

Quality and efficiency share a budget

Total tokens per second is a system-throughput metric. It differs from tokens per second observed by one user. Larger batches can improve throughput while increasing a user's waiting time.

Prefill processes the input context. Decode generates subsequent tokens, often using a key-value cache to reuse intermediate attention state. Long inputs, long outputs, and many concurrent sequences create different resource demands.

Measure quality after changing quantization, speculative decoding, truncation, or sampling. Report a Pareto frontier: configurations where improving one objective requires worsening another. Choose the operating point using the application's latency, cost, and correctness requirements.

Publish an interpretable performance report

MLPerf Inference defines benchmark workloads, quality requirements, and performance scenarios. Its protocol illustrates why throughput should be interpreted with workload and accuracy constraints. Follow the exact rules before claiming an official result.

For an application study, publish hardware and software versions, request counts, test duration, warmup, load levels, latency quantiles, successful throughput, error rate, and cost assumptions. A local script can report useful measurements without claiming MLPerf compliance.

Measure energy with an explicit system boundary and instrumentation if it is part of the comparison. Hardware nameplate power is not measured energy per task. Include idle overhead and utilization assumptions where they affect the conclusion.

Try it yourself

Design a three-load-level test. Report request rate, successful completions, p50 and p95 latency, failure rate, and answer quality at each level.

Can a non-streaming HTTP timer measure time to first token?

No. It measures response completion time under that boundary. First-token timing requires streaming or suitable server instrumentation.
