Chapter 07 / Build evaluations

Design an evaluation dataset

Build representative cases, defensible labels, and splits that resist leakage.

Learning level 45–503 min read + practice2 diagrams · 1 exercise

Sample real work

Start with the decisions users ask the system to make. Sample ordinary requests and known failure cases. Keep a representative set for estimated performance and a stress set for difficult conditions. Report them separately.

Assign stable identifiers to cases. Store the input, expected result, source, difficulty rationale, language, and relevant slices. A slice is a subset such as scanned documents or multi-step requests. Avoid labels that encode the answer in metadata visible to the model.

Synthetic data can expand coverage, but a generator can repeat its own assumptions. Review synthetic examples and include human-authored or real examples when permitted. Do not present a synthetic-only result as a measured production success rate.

Write labels that can be defended

Create a labeling guide with positive examples, negative examples, and ambiguity rules. For subjective tasks, ask multiple annotators to label a shared subset independently. Discuss disagreements before expanding the dataset.

Measure agreement and inspect its causes. Agreement can be high when annotators share the same mistaken assumption. Agreement also changes with class prevalence. Keep disputed cases identifiable and document adjudication.

Some tasks have several valid answers. Store acceptable variants or use a rubric that checks meaning. An exact string match is appropriate only when the expected output is genuinely constrained.

Control contamination

Contamination occurs when evaluation information influences training or selection. Exact duplicates are one route. Translated copies, paraphrases, benchmark explanations, and repeated test-driven prompt edits can also leak information.

Deduplicate before splitting. Check provenance and near-duplicates across splits. Keep private holdouts with controlled access. For external models, complete training-data audits are often impossible. State what you checked and what remains unknown.

Version the dataset and its labels. Correct a broken question transparently and recompute affected comparisons under the corrected version. Do not silently remove tasks simply because your preferred model failed them.

Try it yourself

Write 20 cases for a receipt parser: 10 routine cases, 5 difficult layouts, and 5 unanswerable inputs. Keep the categories explicit.

Should a stress-test score be called expected production accuracy?

No. A stress set has a deliberately different task distribution. Report stress performance separately from a representative production estimate.
