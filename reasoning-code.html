Chapter 15 / Build evaluations

Evaluate reasoning, code, and instructions

Check answers, executable behavior, constraints, and inference budgets separately.

Learning level 65–753 min read + practice1 diagram · 1 exercise

Reasoning outcomes and explanations

A correct final answer provides outcome evidence. A plausible explanation provides a different kind of evidence. Models can produce persuasive explanations for wrong answers, and a correct answer can result from a shortcut.

For mathematics, decide whether the task requires only a numerical answer, a derivation, or a proof. Define equivalence rules for units, fractions, expressions, and tolerance. Symbolic comparison needs domain assumptions; two expressions are not equivalent merely because they match at one sampled input.

For scientific questions, distinguish factual recall, application of a method, and experimental design. Expert review can be necessary when correctness depends on unstated physical or domain assumptions. Keep unresolvable ambiguity out of a supposedly exact-answer metric.

Compute at inference time

A reasoning system can spend additional tokens, sample multiple solutions, use tools, or run a verifier. Compare equal-budget systems when asking about efficiency. Also show performance across budgets when asking about the best attainable result.

Separate the generator from the selector. Pass@k measures whether a successful solution exists among attempts. A real selector must identify it without access to the hidden answer. Best-of-k with an oracle is not the same as a deployable best-of-k system.

An explanation is not direct access to internal computation. Evaluate the correctness of stated steps when the task requires them, but do not treat the text as a complete causal account of how the model reached its answer.

Executable code evaluation

Use hidden tests that cover edge cases and the specification. Include fail-to-pass tests for the requested fix and pass-to-pass tests for existing behavior. A patch that fixes one test while breaking the application should fail the task.

Test code in an isolated environment with resource limits. Separate build failures, dependency failures, test failures, and infrastructure timeouts. Record environment versions because an unchanged patch can behave differently across dependency versions.

HumanEval covers function generation. SWE-bench covers repository issue resolution. EvalPlus strengthens tests for supported code benchmarks. LiveCodeBench uses time-based task collection. These designs provide different evidence; none proves freedom from contamination or correctness for every possible input.

Instruction following and structured output

A verifiable instruction can specify a response format, allowed vocabulary, or a countable requirement. IFEval studies this kind of instruction compliance. The metric should match the instruction rather than a loosely related style preference.

For JSON tasks, test parsing, schema, field types, and semantic values separately. Valid JSON with the wrong amount is a semantic failure. Correct information wrapped in prose can be a format failure when a consuming program requires raw JSON.

Report individual constraints and all-constraints-passed rates. A system that satisfies four of five constraints on every case can have high average constraint accuracy and zero complete-task success.

Try it yourself

Write five tests for a generated median function, including an empty-input policy and an even-length input. State how you will isolate execution.

Why can pass@10 overstate the usefulness of a one-answer product?

Pass@10 can credit any successful attempt among ten. A one-answer product needs either first-attempt success or a validated selector that finds the correct answer within the declared budget.
