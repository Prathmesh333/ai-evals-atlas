Chapter 09 / Build evaluations

Design an experiment before running it

Define the unit of analysis, control confounders, plan power, and interpret rare failures.

Learning level 45–603 min read + practice1 diagram · 1 exercise

Write the estimand

The estimand is the quantity the experiment aims to estimate. For example: the difference in task success between two systems on next month's English support requests, under a fixed tool budget. That sentence specifies more than a benchmark name.

Choose the experimental unit. A request, user, document, repository, or task family can be the independent unit. Several questions from one document share context. Resampling those questions independently can understate uncertainty.

Define the primary outcome and a small set of secondary outcomes before observing results. Record exclusions, stopping rules, retries, and missing-result treatment. A predeclared protocol reduces the temptation to choose whichever analysis favors the candidate.

Separate model effects from system effects

If you change the model, prompt, retriever, and output budget together, you measure a complete system change. You cannot attribute the improvement to the model alone. That combined comparison can still be useful if the deployment decision concerns the whole system.

An ablation changes one component while holding other conditions fixed. A factorial experiment changes several factors in a planned combination, which can reveal interactions. A better prompt might help one model and hurt another.

Randomize execution order when server load or API behavior can drift. Interleave candidate and baseline runs rather than running all baseline cases on Monday and all candidate cases on Friday. Preserve the pairing in analysis.

Plan sample size around the decision

Power is the chance of detecting a specified effect under a specified analysis when that effect exists. A sample-size calculation needs an effect size, expected variability, an error criterion, and assumptions about dependence.

The simple proportion formula in the statistics chapter plans precision for one rate. It is not a universal power calculation for a paired model comparison. Pilot data can estimate how often systems disagree, which influences paired-comparison precision.

If important cases are rare, stratify sampling to obtain enough cases for those slices. Weight results back to the target population when estimating an overall rate. Publish both the sampling proportions and the population weights.

Interpret zero failures and repeated looks

Zero failures does not prove zero risk. With independent trials and zero observed failures, a rough 95% upper failure-rate bound is 3/n. The exact one-sided binomial bound is 1 − 0.05^(1/n). With 100 trials, that bound is about 2.95%.

The bound depends on representative sampling and independence. Repeating one easy prompt 100 times does not establish a failure rate for 100 different production situations.

Repeatedly checking a fixed-sample test and stopping when it becomes significant changes its error rate. Use a fixed stopping rule or a valid sequential procedure. For many comparisons, use a correction or a separate confirmation experiment, and report the selection process.

Try it yourself

Write a one-page protocol for comparing two support assistants. Include the estimand, randomization unit, primary metric, missing-answer policy, and stopping rule.

Does zero failure in 100 independent trials establish a failure rate below 1%?

No. The one-sided 95% upper bound is about 2.95% under the binomial assumptions. More representative independent evidence is needed for a 1% claim.
